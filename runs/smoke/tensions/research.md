### T1: A regular joint look-back session versus no ritual beyond accepting drafts
Roles: organizational learning vs daily user
Side 1: Short, regular debriefs are the one practice with measured payoff (about 25% better performance in roughly 18-minute sessions); without a set moment to ask "did this hold", recorded entries are never tested against later choices and `revisit if` lines rot.
Side 2: A two-person team will not keep both a commit-time habit and a calendar ritual; the baseline itself says the weekly pass lapses first, so the daily cost must stay at one action per decision, with everything riding on commits and the end of agent sessions.
Would settle it: Run 6 to 12 weeks with and without a 15-minute fortnightly look-back. Count later decisions that cite an earlier entry, re-proposals of rejected options, and `revisit if` conditions that came true but were caught only by the review versus by commit-time and agent flags. Also note whether the sessions are still happening by week 4 to 6.

### T2: Agents draft the reason and a human only accepts, versus a record people actually learn from
Roles: daily user vs organizational learning
Side 1: Agents make most commits, so agent drafts with checkable evidence links, accepted or rejected by a human in one action, keep cost near zero and keep the decisions agents made in the log.
Side 2: A lesson counts as learned only when it shows up in a later decision; an agent-written `why` skimmed and accepted may be correct but nobody remembers it, and an unreviewed or lightly reviewed store fills with noise that agents then enforce as constraints.
Would settle it: After 4 to 6 weeks of agent-drafted, human-accepted entries, have each person state from memory the reason for 10 random decisions (5 human-written, 5 agent-drafted) and time lookups of the same. If lookups succeed in under a minute either way, recall does not matter. Also count decisions made versus entries written in each mode, and how many accepted agent drafts are later cited.

### T3: Re-confirming every active entry on a fixed cycle versus leaving entries alone once accepted
Roles: organizational learning vs daily user
Side 1: Stale `active` entries sit in front of every agent session and become constraints; every active entry should be re-confirmed or flagged within N weeks, leaving a dated mark, by a named trigger rather than a person.
Side 2: The only cost the daily user accepts is one action per decision; periodic re-confirmation is another recurring chore with no cue in the commit flow, and checking `revisit if` is already left to agent flags at commit time.
Would settle it: At the three-month mark, sample `active` entries and ask both people whether each still holds. If more than about 1 in 5 no longer hold and are unmarked, re-confirmation is needed. Also log agent actions blocked by a stale `rejected` line.

### T4: Richer entries (reversibility, "confirmed" marks, citations) versus the shortest checkable entry
Roles: organizational learning vs daily user
Side 1: An easy-or-hard-to-undo mark lets review weight scale with how costly a decision is; a "confirmed <date>" slot records what held, not only what failed; citations of earlier IDs are the only countable proof an entry was reused.
Side 2: Each field adds agent context every session, more for a human to verify before accepting, and more to get wrong; extra friction raises the rate of skipped entries, which costs more than the fields gain.
Would settle it: For a month, time entry writing and draft acceptance with and without the extra fields, and count skipped entries (decisions found later in chat or code with no entry), errors found later in accepted entries, and agent re-proposals of rejected options under each format.

### T5: A separate cue for decisions with no acting commit versus everything riding on commits
Roles: organizational learning vs daily user
Side 1: "We won't do X" decisions and decisions made in chat have no acting commit; the fallback "next commit" is a second habit with no cue, and lessons left to an unlinked later moment are the ones that get lost.
Side 2: The daily user wants no extra ritual beyond accept, edit or reject per decision; a new cue outside commits and agent session ends is another habit for a two-person team to drop.
Would settle it: Over a month, list "we won't do X" and chat-only decisions and check how many reach the log within a week under the commit-only design versus with a dedicated cue, and whether the cue is still being used at the end.

### T6: Capping and pruning the active section versus keeping `rejected` lines visible to agents
Roles: organizational learning vs daily user
Side 1: The log must stay short enough for a full read at session start (for example 40 entries or one screen of titles), enforced by a rule that moves or prunes entries well before the 150-entry archive trigger.
Side 2: The daily user needs agents to stop re-proposing rejected options; pruning an entry out of the active section takes its `rejected` lines out of the agent's view, so the same debate returns.
Would settle it: Apply a size cap for a month and count agent re-proposals of options rejected in moved or pruned entries, against lookup time and session-start reading cost with the full log.
