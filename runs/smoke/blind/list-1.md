### T1: Regular shared reviews versus recording decisions without a separate review
Roles: organizational learning vs daily user
Side 1: Short, regular reviews have shown about a 25% performance improvement in sessions lasting roughly 18 minutes. Without a set time to check whether decisions held up, entries go untested against later choices and their reconsideration conditions become stale.
Side 2: Two people are unlikely to maintain both a commit-time habit and a scheduled review. Weekly reviews are expected to lapse first, so recording should require only one action per decision, prompted by commits and agent session endings.
Would settle it: Compare 6 to 12 weeks with and without a 15-minute review every two weeks. Count later decisions citing earlier entries, repeated proposals of rejected options, and met reconsideration conditions caught only in reviews versus commit-time or agent checks. Check whether reviews still happen by weeks 4 to 6.

### T2: Agent-drafted entries with human acceptance versus entries people learn from
Roles: daily user vs organizational learning
Side 1: Agents make most commits, so having them draft entries with checkable evidence links captures their decisions at little cost. A human can accept or reject each draft in one action.
Side 2: An entry has helped only when it informs a later decision. People may skim and accept an accurate agent draft without remembering it, while lightly checked entries can accumulate errors that agents later treat as constraints.
Would settle it: After 4 to 6 weeks, ask each person to recall the reasons for 10 random decisions: 5 human-written and 5 agent-drafted. Time lookups of the same decisions; if both kinds take under a minute, recall does not matter. Also compare decisions made, entries recorded, and later citations of accepted agent drafts.

### T3: Periodic confirmation of active entries versus leaving accepted entries unchanged
Roles: organizational learning vs daily user
Side 1: Stale active entries appear at every agent session and become constraints. Each should be confirmed or flagged within a set number of weeks, with a dated record and a specified trigger that does not depend on someone remembering.
Side 2: The daily user accepts only one action per decision. Periodic confirmation adds a recurring chore outside the commit flow, while checking reconsideration conditions is already assigned to agent checks at commit time.
Would settle it: After three months, sample active entries and ask both people whether each still holds. If more than about one in five are no longer valid and remain unmarked, periodic confirmation is needed. Also count agent actions blocked by stale records of rejected options.

### T4: More entry fields versus the shortest checkable entry
Roles: organizational learning vs daily user
Side 1: Recording how hard a decision is to undo allows more review for costly choices. A dated confirmation records what held up, and references to earlier entry IDs provide countable evidence that entries informed later decisions.
Side 2: Every field adds material for agents to read, work for humans checking drafts, and opportunities for errors. That friction can increase skipped entries enough to outweigh the value of the extra fields.
Would settle it: For a month, compare entry-writing and draft-acceptance times with and without the extra fields. Count decisions later found in chat or code without entries, errors later found in accepted entries, and repeated agent proposals of rejected options under each format.

### T5: A separate recording prompt for decisions without commits versus commit-based recording
Roles: organizational learning vs daily user
Side 1: Decisions made only in chat, including decisions against doing something, may produce no commit. Waiting for the next commit requires remembering an unrelated follow-up, making those decisions easy to lose.
Side 2: The daily user wants only one accept, edit, or reject action per decision. Adding a prompt beyond commits and agent session endings creates another habit that two people may stop maintaining.
Would settle it: For a month, list chat-only decisions and decisions against doing something. Compare how many reach the log within a week with commit-based recording alone versus a dedicated prompt, and check whether that prompt is still being used at the end.

### T6: Limiting the active section versus keeping rejected options visible to agents
Roles: organizational learning vs daily user
Side 1: The log must remain short enough to read fully at session start, such as 40 entries or one screen of titles. A rule should move or remove entries well before the archive threshold of 150 entries.
Side 2: The daily user needs agents to stop proposing rejected options. Moving or removing entries hides those rejections from agents and allows the same discussions to return.
Would settle it: Apply a size limit for a month and count repeated agent proposals of options rejected in moved or removed entries. Compare those repeats with lookup time and the cost of reading the full log at session start.
